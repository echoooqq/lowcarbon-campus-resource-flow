## 摘要

本报告完整阐述了《低碳校园资源循环流转桌面系统》的设计与实现过程。该系统面向高校校园场景，为学生提供闲置物品发布、浏览、交易、评价的全生命周期管理，同时通过统计报表量化二手资源流转的低碳贡献。

技术栈选型为 **Java 21 + Swing + SQLite + JUnit 4**，全程遵循课程要求的模块化、面向对象、设计模式、测试驱动、防御性编程等核心方法论。系统共包含 **52 个主程序源文件（9035 行）+ 14 个测试源文件（4219 行）**，累计 **13254 行 Java 代码**，实现 **278 个单元测试全部通过**。

设计模式方面，落地了 **单例、工厂、策略、观察者** 四种模式，覆盖数据层、业务层和跨模块协作。

**关键词**：软件构造；面向对象；设计模式；JUnit 测试；Swing GUI；SQLite 嵌入式数据库；低碳

## 一、引言

### 1.1 研究背景

在高校校园中，每届毕业生离开时都会留下大量仍有使用价值的闲置物品——教材、电子数码配件、文体用品、小家电等。这些物品的处置方式多为直接丢弃或当作废品售卖，既浪费资源又增加碳排放。根据环保机构数据，每流通 1 本二手教材可节约约 6 kg CO₂（造纸能耗 + 运输能耗）。

### 1.2 问题分析

| 痛点 | 传统做法 | 本系统解决方案 |
|------|---------|---------------|
| 信息不对称 | 线下张贴 / 班级群零散发布 | 统一物品大厅 + 分类筛选 + 关键词搜索 |
| 交易无记录 | 口头约定，事后难追溯 | 完整流转记录，状态机驱动 |
| 缺乏信任机制 | 凭感觉交易 | 信用分体系 + 双向评价 |
| 低碳贡献不量化 | 环保概念模糊 | 每笔成交自动折算碳排放节约量 |

### 1.3 研究目标

构建一个功能完整、架构清晰、可部署运行的桌面端软件系统，覆盖以下 **8 项强制交付要求**：

| # | 要求 | 本系统覆盖情况 |
|---|------|---------------|
| 1 | 模块化软件构造 | 5 层清晰分层（entity → dao → service → gui + factory/observer/util） |
| 2 | 面向对象设计 | 9 个实体类 + 4 种设计模式 |
| 3 | 数据持久化 | SQLite 嵌入式数据库，5 表 3 索引 |
| 4 | 用户交互 GUI | Swing + CardLayout 导航外壳，9 个 Panel |
| 5 | 软件重构 | 消除 10+ 处重复坏味道，统一枚举 getLabel() |
| 6 | 数据库编程 | JDBC + PreparedStatement + 事务控制 + 外键约束 |
| 7 | 设计模式（≥3 种） | 单例 + 工厂 + 策略 + 观察者 = **4 种** |
| 8 | JUnit 测试 | 278 个测试（DAO 83 + Service 124 + Util 33 + 集成 14） |

## 三、系统设计

### 3.1 总体架构（五层 + 横切关注点）

```
┌──────────────────────────────────────────────────────────────┐
│                         GUI Layer                              │
│        MainFrame (CardLayout) + 9 Panel + 1 Dialog            │
├──────────────────────────────────────────────────────────────┤
│                      Service Layer                             │
│   UserService │ ItemService │ TransactionService │            │
│   ReviewService │ StatisticsService │ AdminService            │
│   ──────────────────────────────────────                      │
│   Observer Pattern：ItemStatusSubject → CreditAdjustObserver  │
│   Strategy Pattern：ItemFilterStrategy 组合筛选               │
├──────────────────────────────────────────────────────────────┤
│                        DAO Layer                              │
│   Interface + JDBC Impl：5 × (Dao + DaoImpl)                  │
├──────────────────────────────────────────────────────────────┤
│                      Entity Layer                              │
│   9 个 POJO + 4 个枚举                                        │
├──────────────────────────────────────────────────────────────┤
│                    Cross-Cutting                               │
│   DaoFactory │ ServiceFactory │ DatabaseManager（单例）       │
│   Validator │ PasswordUtil │ CsvExporter                      │
│   DaoException │ BusinessException                            │
└──────────────────────────────────────────────────────────────┘
```

**分层规则**：
- 上层依赖下层，下层不依赖上层
- DAO ↔ DB 边界：所有 SQL 封装在 DAO 中，Service 不写 SQL
- Service 是事务边界，DAO 是数据原子操作
- GUI 只调 Service，不调 DAO

### 3.2 核心实体模型

| 实体 | 字段 | 关键约束 |
|------|------|---------|
| **User** | userId, username, passwordHash, salt, role, creditScore, createTime | username UNIQUE, role 枚举(USER/ADMIN) |
| **Item** | itemId, publisherId, name, categoryId, description, price, tradeType, status, tags, publishTime | status 枚举(ON_SALE/RESERVED/SOLD/OFF_SHELF) |
| **Category** | categoryId, name, description | name UNIQUE，预置 4 条 |
| **Transaction** | recordId, itemId, buyerId, status, createTime, completeTime | status 枚举(PENDING/APPROVED/COMPLETED/REJECTED/CANCELLED) |
| **Review** | reviewId, recordId, reviewerId, rating, comment, createTime | rating 1~5 |

**关联**：User 1:N Item（发布）；User 1:N Transaction（买卖）；Item 1:1 Transaction；Transaction 1:2 Review（买卖互评）。

### 3.3 数据库设计（SQLite）

```sql
-- 5 张表 + 3 索引 + 外键约束
PRAGMA foreign_keys = ON;

CREATE TABLE user ( ... );          -- 用户账号
CREATE TABLE category ( ... );      -- 物品分类
CREATE TABLE item ( ... );          -- 闲置物品
CREATE TABLE transaction_record ( ... );  -- 流转记录
CREATE TABLE review ( ... );        -- 评价

CREATE INDEX idx_user_username ON user(username);
CREATE INDEX idx_user_role    ON user(role);
CREATE INDEX idx_item_publisher ON item(publisher_id);

-- 预置分类（4 条）
INSERT OR IGNORE INTO category (name, description)
VALUES ('教材', '数码配件', '文体用品', '生活物资');
```

**设计决策**：
- 使用 `INSERT OR IGNORE` 保证 `schema.sql` 幂等可重复执行
- 所有时间存 Unix 毫秒时间戳（跨时区无歧义）
- 密码存 SHA-256 + 随机盐值（`PasswordUtil`）
- 数据库文件命名 `lowcarbon.db`，Jar 同级目录，零配置

## 四、设计模式应用

### 4.1 单例模式（Singleton）

**应用位置**：`DatabaseManager` + `ServiceFactory`

**目的**：全局唯一数据库连接管理器 + 唯一 Service 实例。

**为什么必须用单例**：
1. `DatabaseManager` 维护 SQLite JDBC URL 和 schema 执行，多个实例会导致重复建表、连接泄露
2. `ServiceFactory` 的单例缓存是 **观察者模式生效的前提**：`ItemService` 上注册的观察者列表必须在所有调用方之间共享。如果 `AdminService` 内部持有的 `ItemService` 和外部注册观察者的 `ItemService` 是不同实例，观察者就收不到通知

**实现方式**：静态 final 字段 + DCL 双重检查锁（DatabaseManager）/ 静态初始化（ServiceFactory）

```java
// ServiceFactory — 静态初始化，类加载时唯一实例
public final class ServiceFactory {
    private static final ItemService ITEM_SERVICE =
            new ItemService(DaoFactory.getItemDao(), DaoFactory.getUserDao(), ...);

    public static ItemService getItemService() { return ITEM_SERVICE; }
    // ...
}
```

**集成测试验证**：`TestObserver_AdminForceOffShelfAlsoTriggers` 证明 ServiceFactory 单例化后，AdminService 调用 itemService.adminTakeOffShelf() 确实触发了外部注册在同一个 ItemService 实例上的 CreditAdjustObserver。

### 4.2 工厂模式（Factory）

**应用位置**：`DaoFactory` + `ServiceFactory`

**目的**：集中创建 DAO / Service 实例，解耦调用方与具体实现。

**好处**：
- Service 层只依赖 `DaoFactory.getUserDao()`，不直接 `new UserDaoImpl()`，方便测试替换 Fake DAO
- DAO 实现可能需要变化（比如日后迁移 MySQL），Service 层零改动
- `ServiceFactory` 同时承担 **依赖装配** 职责（按拓扑排序：UserService → ItemService → AdminService）

### 4.3 策略模式（Strategy）

**应用位置**：`ItemService.searchOnSale()`

**目的**：支持分类 / 关键词 / 价格区间 **自由组合** 的物品筛选。

**落地结构**：

```
ItemFilterStrategy (接口)
├── CategoryFilterStrategy      — 按分类 ID 筛选
├── KeywordFilterStrategy       — 按名称关键词模糊匹配
├── PriceRangeFilterStrategy    — 按价格区间筛选
└── CompositeFilterStrategy     — 组合多个策略（AND 语义）
```

**调用示例**：
```java
// 分类=教材 AND 关键词="数学" AND 价格=[20,30]
itemService.searchOnSale("数学", 1L, 20.0, 30.0);
```

**可扩展性**：新增筛选条件（比如只看免费物品、只看信用分 ≥ 120 的卖家）只需实现新的 Strategy 类，`searchOnSale` 主流程零改动。

### 4.4 观察者模式（Observer）

**应用位置**：`ItemStatusSubject`（接口） ↔ `CreditAdjustObserver`

**目的**：物品状态变更时，自动触发"信用分扣减"等副作用，主业务流程不直接耦合这些逻辑。

**触发链路**：
```
ItemService.takeOffShelf()
    → transitionStatus(ON_SALE → OFF_SHELF)
        → 通知所有观察者：onStatusChanged(itemId, old, new)
            → CreditAdjustObserver
                → userService.adjustCreditScore(publisherId, -5)
```

**关键设计**：
- 观察者列表在 ItemService 上维护（ServiceFactory 单例保证全局唯一）
- 通知异常被捕获并记录日志，**不会中断主业务流程**（`testObserver_ExceptionDoesNotBreakMainFlow` 验证）
- 观察者通过工厂获取 Service 依赖，ItemService 不需要知道观察者的具体逻辑

**为什么用观察者**：如果不用观察者，信用分扣减逻辑就要写在 takeOffShelf / adminTakeOffShelf 两个方法里。管理员下架以后可能还要触发"日志审计"、"消息通知"等新动作，每次都要改 ItemService 代码。用观察者模式后，新增副作用只需要加新 Observer 类，**Open-Closed 原则**。

## 五、面向对象设计

### 5.1 封装（Encapsulation）

- `DatabaseManager`：JDBC URL 构造、schema.sql 加载、Connection 创建都私有化，外部通过 `getConnection()` 获取
- 实体类：字段 private + 标准 getter/setter，不暴露内部状态
- DaoFactory / ServiceFactory：构造器私有，防止实例化

### 5.2 继承（Inheritance）

- `DaoException extends RuntimeException` → 包装 SQLException
- `BusinessException extends RuntimeException` → 业务层统一异常

### 5.3 多态（Polymorphism）

- DAO 接口模式：`UserDao` 接口 + `UserDaoImpl` 实现，测试时替换为 Fake DAO
- 策略接口：`ItemFilterStrategy` 四种实现可任意组合
- 观察者接口：`ItemStatusObserver` 可注册多个不同逻辑的观察者

### 5.4 抽象数据类型（ADT）

- `TransactionStatus` 枚举：6 个状态 + `canTransitionTo()` 状态机方法，状态迁移规则封装在枚举内部
- `ItemStatus` 枚举：同理，`statusLabel` + 状态约束方法

## 七、防御性编程

### 7.1 SQL 注入防护

所有 SQL 参数使用 **PreparedStatement**，零字符串拼接：
```java
// ✅ 正确
PreparedStatement ps = conn.prepareStatement("SELECT * FROM user WHERE username = ?");
ps.setString(1, username);

// ❌ 严格禁止
String sql = "SELECT * FROM user WHERE username = '" + username + "'";
```

### 7.2 输入校验（Validator）

```java
// 用户输入必经 Validator 校验
Validator.requireUsername(username);    // 长度 3~50, 字母数字下划线
Validator.requirePassword(password);    // 长度 ≥ 6
Validator.requireNonBlank(name, "物品名称");
Validator.requirePrice(price);          // ≥ 0
```

### 7.3 异常分层处理

```
SQLException
    ↓ DAO 层 catch
DaoException（包装 + 日志）
    ↓ Service 层 catch
BusinessException（友好消息 + 根因保留）
    ↓ GUI 层 catch
弹窗显示 "用户名或密码错误，请重试"
```

### 7.4 资源自动关闭

所有 Connection / PreparedStatement / ResultSet 使用 **try-with-resources**：
```java
try (Connection conn = DatabaseManager.getConnection();
     PreparedStatement ps = conn.prepareStatement(sql)) {
    // ...
}  // 自动关闭，杜绝资源泄露
```

### 7.5 观察者异常隔离

```java
try {
    observer.onStatusChanged(itemId, oldStatus, newStatus);
} catch (Exception e) {
    LOGGER.warning("观察者执行异常，已忽略");
}
// 主业务流程继续，不会因为观察者故障而中断
```

| 数据库字段 | lower_snake_case | `publish_time`, `user_id` |

### 9.4 注释密度

- 所有类有 Javadoc（职责、作者、创建日期）
- 所有 public 方法有 Javadoc（@param, @return, @throws）
- 复杂业务逻辑 + 行内 `//` 注释

| 第九章 基于复用的软件构造 | ✅ | **4 种设计模式**（超要求 ≥3 种） |

### 11.2 技术亮点

1. **观察者模式 + 工厂单例**：验证了"设计模式不是孤立落地的"——观察者需要 Factory 提供单例 Service 才能真正生效，这个发现是集成测试带来的真实问题
2. **状态机驱动的交易流程**：`TransactionStatus.canTransitionTo()` 把状态迁移规则封装在枚举内部，Service 层调用时自然遵守规则
3. **双层异常包装**：`SQLException → DaoException → BusinessException → GUI 弹窗`，既不丢失根因又不让 GUI 看到技术细节
4. **集成测试发现了真实 Bug**：278 个测试中，**14 个集成测试发现了 4 个真实问题**（观察者不生效、Factory 不单例、类型不匹配、启动脚本），证明集成测试的价值远大于单元测试

### 11.3 局限与展望

| 局限 | 改进方向 |
|------|---------|
| 密码盐值未持久化到用户表 | 已持久化（user.salt），但可考虑每 90 天重新加盐 |
| 管理员需手动提升（无注册入口） | 可添加"管理员邀请码"机制 |
| 无网络功能 | 课程要求桌面端，后续可加 HTTP 服务端让多个客户端同步 |
| Swing 外观朴素 | 可换成 FlatLaf 等第三方 Look & Feel |
| 无单元测试覆盖 GUI 层 | Swing GUI 测试需 AssertJ-Swing 等额外库，保持轻量暂不引入 |
